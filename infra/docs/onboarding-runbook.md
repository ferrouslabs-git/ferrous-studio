# Onboarding runbook — what `terraform apply` does, and how to extend it

This is the generic version of `ferrous-humanity-processmapper`'s
`docs/shared-rds-new-product.md` (the runbook for putting a new product on
the shared VPC/ALB/ECS cluster/RDS instance). `infra/terraform/` automates
every step below for the product named in `app.config.json`. Read this if a
step fails and you need to investigate by hand, or if you're adding a step (a
real domain, MFA, a second app client, etc).

## The shared instance

| Endpoint | `ferrous-internal-tools-database.crwye4eoshr1.eu-west-1.rds.amazonaws.com:5432` |

| ECS cluster | `default` |
| ALB | `processmapper-staging-alb` (name is historical — it's the shared ALB) |

All of the above are already recorded in `app.config.json`'s `shared_infra`
block — `infra/terraform/locals.tf` reads them from there via
`jsondecode(file(...))`, not from this table.

## Pattern this template follows

**One database per product per environment** (not one shared database with a
schema per environment): `<product>_staging` / `<product>_prod`, owned by
`<product>_staging_app` / `<product>_prod_app`, `public` schema, plain
`DATABASE_URL` per env. See `backend/app/database.py` for why (blast radius,
backups, no schema/search_path plumbing in the app).

**One Cognito user pool per environment**: `<product>-staging` /
`<product>-prod` (`infra/terraform/cognito.tf`). Staging and prod users are
entirely separate — nothing you sign up with in staging exists in prod.

## What `terraform apply` creates (`infra/terraform/`)

1. **Security group** `<product>-ecs-sg` (`security_group.tf`): allows the
   ALB to reach the task on `container_port`, and adds a rule to the shared
   RDS security group letting the task reach RDS on 5432.
2. **RDS roles + databases** (`rds.tf`, via a `null_resource` local-exec
   provisioner that runs `scripts/create-rds-roles.sh`): the RDS instance is
   private, so this can't run from Terraform directly — it executes as a
   one-off command inside the `pg-admin` Fargate task (a `postgres:18`
   container with master credentials injected; must already exist in the
   account — see step 1 of the processmapper runbook if it doesn't).
   Passwords are generated by Terraform (`random_password`, in `secrets.tf`)
   so they never need typing by hand.
3. **Secrets Manager** (`secrets.tf`): `<product>/staging/DATABASE_URL`,
   `<product>/prod/DATABASE_URL`, built from the same generated passwords.
4. **Cognito** (`cognito.tf`): two user pools + app clients + hosted-UI
   domains, `<product>-staging` and `<product>-prod`.
5. **ECR repository** (`ecr.tf`) named `<product>`.
6. **IAM** (`iam.tf`): the shared `ecsTaskExecutionRole` gets an inline
   policy scoped to `secretsmanager:GetSecretValue` on `<product>/*` only; a
   dedicated `<product>-task-role` is created for the app's own AWS calls
   (Cognito admin actions, S3, etc. as you add them).
7. **Target groups** (`target_groups.tf`): `<product>-staging-tg` /
   `<product>-prod-tg`, health check `/api/health`.
8. **ALB listener rules** (`alb_listener_rules.tf`): a host-header rule per
   environment on the shared ALB's plain **HTTP:80** listener, at
   `alb_priority_base` / `alb_priority_base + 1` from `app.config.json`. This
   is not optional, even before you have a domain: `aws ecs create-service
   --load-balancers` rejects a target group that isn't already associated
   with a load balancer, and only a listener rule referencing it creates
   that association. It doesn't expose anything on the public internet by
   itself (nothing resolves the placeholder `.invalid` hostname) — see the
   next section for wiring a real, HTTPS domain.

What Terraform does **not** create: the ECS task definition or service.
Those change on every deploy (new image tag), so `infra/scripts/deploy-*`
registers the task definition and creates/updates the service imperatively
via the AWS CLI, reading `terraform output` for the security group, target
group, task role, ECR repo and Cognito values it needs.

## What it deliberately leaves manual: HTTPS on a real domain

By default, `app_public_url` in `infra/terraform/locals.tf` resolves to a
placeholder `https://<env>.<product>.invalid` URL for Cognito's
callback/logout URLs and the HTTP listener rule's host-header condition
(RFC 2606 `.invalid` — guaranteed to never resolve), so the whole pipeline —
including a working ECS service — works without a domain. When you have a
real domain, set `domain.root` in `app.config.json`, run `terraform apply`
again (the Cognito app clients and the HTTP listener rule both pick up the
real hostnames), then add HTTPS by hand:

```bash
# a. ACM cert covering both the root and the staging subdomain
CERT=$(aws acm request-certificate --region eu-west-1 \
  --domain-name '<domain>' --subject-alternative-names 'staging.<domain>' \
  --validation-method DNS --query CertificateArn --output text)
# ...create the DNS validation records, wait for ISSUED, then:
aws elbv2 add-listener-certificates --region eu-west-1 \
  --listener-arn <alb_https_listener_arn from app.config.json> \
  --certificates CertificateArn=$CERT

# b. Host-header rules on the shared HTTPS listener, same priorities as the
#    HTTP ones Terraform already created (alb_priority_base / +1). Target
#    group ARNs: `terraform output target_group_arns`.
aws elbv2 create-rule --region eu-west-1 \
  --listener-arn <alb_https_listener_arn> \
  --priority <alb_priority_base> --conditions Field=host-header,Values='<domain>' \
  --actions Type=forward,TargetGroupArn=<prod target group arn>
aws elbv2 create-rule --region eu-west-1 \
  --listener-arn <alb_https_listener_arn> \
  --priority <alb_priority_base + 1> --conditions Field=host-header,Values='staging.<domain>' \
  --actions Type=forward,TargetGroupArn=<staging target group arn>

# c. DNS: point both domains at the shared ALB
#    (alias/CNAME -> the ALB's DNS name)
```

> **Routing gotcha inherited from the shared ALB:** the HTTPS listener's
> *default* action forwards to processmapper staging. Any hostname you don't
> add a rule for lands there — always add explicit host-header rules.
>
> This step could be folded into Terraform too (an `aws_acm_certificate` +
> `aws_lb_listener_certificate` + `aws_lb_listener_rule` per environment) —
> it's left manual here because ACM DNS validation needs a pause for the
> validation records to be created out-of-band, which doesn't fit a single
> `terraform apply`. If you want it automated, that's the natural next step.

## Instance-level housekeeping (as products accumulate)

- **Connections** — the per-role `CONNECTION LIMIT 20` set by
  `scripts/create-rds-roles.sh` keeps one product from starving the shared
  instance's connection pool.
- **Noisy neighbours** — CPU/IO are shared across every product on this RDS
  instance; a heavy staging batch job affects everyone else's prod too.
- **Storage** — one product filling the disk stops all of them.
